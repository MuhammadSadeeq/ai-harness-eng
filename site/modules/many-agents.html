Many agents: when and how

A parent that starts sub-agents can do more work, and it can multiply the cost of every answer. Learn the two honest reasons to add one, and how to check what it returns.

  • Loop & state
  • Context & memory
  • Verification & evals

55 minutes

By the end you can

  1. Name the two honest reasons for many agents (parallel work, context isolation) and the warning that comes with them.
  2. Compare five topologies by cost, wall-clock time and failure modes.
  3. Choose an isolated or a forked context for a sub-agent and explain the trade-off.
  4. Write a sub-agent brief whose result can be checked.
  5. Treat a multi-agent system as a distributed system: timeouts, partial failure, conflicting writes, cleanup.

Three notes, read twice

A parent has three notes to summarise. It starts a reader for each note, then it asks again for each one, just to be sure. Predict what the run does next.

Without JavaScript, the question is: a parent has three notes. It starts a reader for each, then starts a reader again for each note. What happens to the summary, and what happens to the cost?

  1. The summary is the same, and the run costs more: each repeat is a new reader with its own input.
  2. The repeats disagree with the first readers, so the summary is wrong.
  3. Sub-agents run in parallel for free, so the cost stays the same.

The summary is right. The harness let each repeat start a reader, and nothing in the run said the repeats were not needed. The run ended done, so the pass looked clean.

Two honest reasons, and the bill

An orchestrator is the parent agent. It starts sub-agents, gives each one a brief, and reads what they return. A sub-agent is another loop with its own turns, its own context and its own bill.

The first honest reason is parallel work: several pieces that do not wait on each other. The second is context isolation. A long, noisy search can fill a context, and a sub-agent keeps that search out of the parent's window. Both reasons are about the work, not about how the system looks.

Without JavaScript, the question is: which is an honest reason to add a sub-agent?

  1. It makes the work look bigger in a demo.
  2. It keeps a long, noisy search out of the parent's context, so the parent keeps its room.
  3. It lets two agents make a shared decision without talking to each other.

The warning comes with both reasons. Each sub-agent costs its own input and output, and its answer is a claim, not a fact. A multi-agent system also fails in parts: a reader times out, a brief drops a constraint, two workers write the same file. The parent has to decide what to do with what it got back.

Without JavaScript, the question is: a sub-agent times out and returns nothing. What should the parent do?

  1. Treat the silence as a finding that nothing was there.
  2. Decide with what it has, and say which note is missing.
  3. Start the same reader again with no limit.

A fan-out starts several sub-agents at once, one per piece of work. A topology is the shape of the whole system: who starts whom, who reads whose output, and where work waits. The lab compares five shapes for one task. Each one buys something and pays for it in cost, wall-clock time and a set of failure modes.

Without JavaScript, the question is: a generator and an evaluator run in a loop. What failure should you watch for?

  1. The evaluator approves its own style of work.
  2. The two agents need too much memory to run.
  3. The loop costs nothing, because each side is short.

A sub-agent starts in one of two contexts. An isolated context starts from its brief alone. A forked context starts from the parent's messages so far, plus the brief. Isolated is cheaper on the first request. Forked knows more, and its first request is larger. Choose the one the decision needs.

Without JavaScript, the question is: a sub-agent must judge a decision that depends on the parent's last ten messages. Which context does it need?

  1. An isolated context, so it is cheaper.
  2. A forked context, so it starts from the parent's messages.
  3. No context at all, and the brief alone.

Pick the shape, then write the brief

The lab is five shapes for one task: a bug report that touches more than one file, with the tests that show it. Choose a shape, read its cost and wall-clock ratios against one agent, and read how it fails. Then switch the sub-agent between isolated and forked. The toggle runs the same sub-agent tape on two boards and reads its input from each run.

The ratios are illustrative. They are the course's model, not measurements on any model. What the lab shows is the shape of the trade-off.

Write the brief

A brief should let you check the answer. It names the task, the files the sub-agent may read, and the fields its result must return. Without a field, the result has nothing for the parent to check, and the parent is guessing.

Without JavaScript, the question is: which brief lets the parent check the result when it comes back?

  1. Find something useful in the notes.
  2. Read notes/a.txt. Return the date as 'date: value'.
  3. Do whatever is needed and report back.

Without JavaScript, open katas/F1-brief/test_kata.py. Each test names one rule of a brief that can be checked.

Prove it on the same notes

The sprawl board has no cap. The capped board refuses a reader that starts for a job it already has. The bench runs the same notes on both boards and reads what each run spent.

These runs are scripted, so they repeat exactly. Real models differ in how often they ask again, and a real sub-agent can fail in ways no script shows. The cost is what the run spent, not what the work was worth.

Keep it

Add agents for a reason, not for a picture.

Why does a sub-agent get a brief?
It starts from the brief, or from the parent's messages with the brief added. So the brief must name the task, the files and the result.
What is an orchestrator?
The parent that starts workers, gives each one a brief, and reads what they return.
What does an isolated context cost against a forked one?
Fewer input tokens on the first request, and no view of the parent's messages.
Name the two honest reasons for many agents.
Parallel work, and keeping a separate piece of work out of the parent's context.
A sub-agent's answer comes back. Is it a fact?
No. It is a reader's answer. Check it against the file or the field the brief named before the parent relies on it.
What is a fan-out?
Starting several sub-agents at once, one per piece of work, and reading their results together.

Say it out loud

  1. Your task needs five files read. Would you add sub-agents? Argue for and against, and say what you would check.
  2. Compare one agent with an orchestrator and workers on cost and failure. Which context do the workers get, and why?
