Notes read one at a time

This run reads a set of notes and writes a summary. It passes. Predict what it costs next to a run that reads the same notes and gets the same answer.

Without JavaScript, the question is: this run asks for several notes in one reply. The model then asks for them one reply at a time. What does the harness do with the results of the first reply?

  1. It sends them all back in one user message, as the model expects.
  2. It sends each result in its own user message, one after another.
  3. It drops every result after the first.

The run passed, and the model did what it was told. The harness had handed back each result in its own message. After that the model read one note per turn, and the run cost more than it needed to.

The model asks, the harness acts

A reply from the model is a list of blocks. A block that asks for a tool is a tool_use block: it has an id, a name and an input. The stop reason tool_use means the model is calling a tool and expects the application to run it. The model only writes the request. Some docs call this function calling.

The harness reads each block by its type, runs the named tool with its input, and records the output. Parallel tool calls are several requests for tools in one reply, and their results go back together in one user message.

def read_file(path):
    return {"a.txt": "Buy milk."}.get(path, "missing")


reply = {"stop_reason": "tool_use", "content": [
    {"type": "tool_use", "id": "t1", "name": "read_file", "input": {"path": "a.txt"}},
    {"type": "tool_use", "id": "t2", "name": "read_file", "input": {"path": "b.txt"}},
]}
for block in reply["content"]:
    if block["type"] == "tool_use":
        print(block["id"], read_file(**block["input"]))
t1 Buy milk.
t2 missing

Run the code with the Run key. Each call keeps the id of its tool use request, so the output can be matched back to the call that asked for it.

Without JavaScript, the question is: the model wants a file read. Who runs the read?

  1. The model runs it, then reports the result.
  2. The harness runs it, then sends the result back to the model.
  3. Nobody. The reply is the answer.

A tool definition

The model knows a tool only through its tool definition: a name, a description and an input_schema. The schema lists the fields the tool takes, their types, and which of them are required.

{
  "name": "read_file",
  "description": "Read a file in the workspace. Use it when you need the text of one file.",
  "input_schema": {
    "type": "object",
    "properties": {"path": {"type": "string", "description": "The file path, relative to the workspace"}},
    "required": ["path"]
  }
}

Without JavaScript, the question is: which set is the whole of a tool definition?

  1. A name, a description and an input schema.
  2. A name and a function body.
  3. A prompt that explains the tool.

Answer every call in one message

Each tool_result answers one call. Its tool_use_id is the id of the tool use request that the result answers.

A failed call is still an answer. The is_error field is optional, and it is set to true when the tool execution resulted in an error. A call the harness does not run still gets a result: it needs a tool_result with is_error set to true and a brief explanation.

The results of one reply go back together. Return one tool_result for each tool_use block, all together in the next user message.

The parallel tool use docs say that formatting tool results incorrectly in the conversation history 'teaches' Claude to avoid parallel calls. The scripted model in the break does the same: once the results split, it asks for one note at a time.

A tool is a user interface for a model

A person reads a tool's name and help text. A model reads only the definition, so the name, the description and the schema are its whole picture of the tool. A poor definition is a poor interface, and the model misuses the tool in the same way a person would.

Without JavaScript, the question is: a model keeps calling a tool with the wrong argument. What most likely helps?

  1. A clearer description and a described input schema.
  2. A longer wait between calls.
  3. Removing the tool from the list.

Keep it

The model asks; the harness acts.

What does the model do when it wants a tool run?
It writes a tool request and expects the application to run it. It does not run the tool. The harness does.
What stop reason tells the harness that a tool run is needed?
tool_use. The harness runs the tools, then calls the model again with the results.
What three parts make a tool definition?
A name, a description and an input schema.
What does input_schema say?
The fields the tool takes, their types, and which of them are required.
What must each tool_result carry?
The tool_use_id of the call it answers.
How do you mark a failed call?
Set is_error to true, an optional tool_result field, when the tool execution resulted in an error.
Where do the results of one reply go?
All together in one user message, sent after the reply.
Why is a tool a user interface for a model?
The model sees only the definition. The name, the description and the schema are its whole picture of the tool, so a poor definition leads to misuse.
