Rein 5: a trace

Rein records every model call, verdict and tool call in a file as it happens, in the course's trace format. Then you open that file in the Replay Deck and read the run line by line.

A bill with no reason in the total

A run costs far more than the last one, and the total is high. Predict which line of the trace shows why.

Without JavaScript, the question is: A run costs far more than the last one. The total in run_end is high. Which line do you read first?

  1. The first model_call, because the run starts there.
  2. The model_reply lines, which carry the tokens and cost of each call, so you can see the turn where the cost moves.
  3. The run_end line alone, because it has the total.

The total says the run was expensive. It does not say why. The per-call lines do, and they are only there if the trace wrote them.

One line per event

The tracer writes one line of JSON for each event as it happens, so the file is a JSONL record of the run. Each line carries v, run, seq, t in milliseconds, turn, agent, kind and wire, then the kind's own fields. A run emits six kinds: run_start once; model_call and model_reply for each turn; permission for each verdict; tool_call for each tool call, denied ones too; and run_end at the end.

Without JavaScript, the question is: Which field shows that a line is missing from a file?

  1. seq, because it counts one run's lines from 0 with no gaps.
  2. t, because it is the time.
  3. run, because it names the run.

seq counts one run's lines from 0. A jump in seq means a line is missing, and the deck names the line where the jump is.

Without JavaScript, the question is: The last line of a run says status done. Which kind of line is it?

  1. run_end, which closes the run and carries its status.
  2. model_reply, because it is the last thing the model said.
  3. permission, because the last verdict ends the run.

Anything that looks like an API key is replaced before the line is stored, so the file can be shared. The screen still shows what the model said, so check the file, not the screen, before you send it.

A trace is the record of one run. The wider practice of reading traces is in C12 · Observability: traces you can read.

Without JavaScript, the question is: A tool result contains a string that looks like an API key. What does the trace store?

  1. The key, because the trace exists for debugging.
  2. [REDACTED] in its place, so the file can be shared.
  3. Nothing: the line is not written at all.

These runs are scripted, so they repeat exactly. A real run's cost depends on the model and the prices of the day, which the trace records as they were.

Keep it

If it isn't in the trace, it didn't happen.

What does every line of the trace carry?
v, run, seq, t in milliseconds, turn, agent, kind and wire, then the kind's own fields.
What does seq tell you about a file?
It counts one run's lines from 0 with no gaps, so a missing line shows as a jump in seq.
