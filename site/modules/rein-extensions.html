Rank by what you learn and can show

An extension is a change to Rein that you can name and measure. There are many, and the one that sounds most impressive is seldom the right one to build first. The course ranks extensions by two things: what building one teaches you, and what it lets a reviewer check. The ranking is the course's judgment. It makes no claim about any job market.

  1. A process check in the eval grader. It teaches measurement: a grader that reads how the agent got to its result, not only the files it left. A reviewer can see the check, its criterion and its number.
  2. A permission rule for writes. It teaches the permissions wire: what the agent may change, and a run that proves it stayed inside that limit.
  3. A tool-call budget. It teaches guards, which H8 covers, so the new lesson is what a guard does to the numbers.
  4. A rewritten tool description. It teaches the tools wire, but a scripted run cannot decide it: a scripted model replays its replies whatever the description says. Only a live run could show the effect, and the course records no real-model numbers (D-038).

Two rules hold for all four. Write the criterion before the code. Then report what the number did, not what you hoped it would do.

Without JavaScript, the question is: which extension should a learner scope first, by the course's judgment?

  1. The one that sounds most impressive.
  2. The one that teaches measurement and that the package can measure.
  3. The one that needs no numbers at all.

Do: scope one, run it, report it

Scope before code

The worked example is the first extension, the process check. Its scope went in writing before any code, and the rest of this paragraph is that scope. The question: does the check change how many trials pass on the D1 suite? The rule: a trial passes only if its outcome check passes and every write_file call targets a file the run had read first. The command and seed: the command below, on the board with no changes. Trial k runs with seed k, for k from 1 to 10. The decisive number: passes out of ten, for each task. The prediction went in with the scope too: no change, because the held-out tasks read every file before they write it.

Run the baseline on your machine. The scripted run needs no key:

Run these from the repository root, on your machine, after installing rein once with python -m pip install -e ./rein.

python -m rein eval --eval scenarios/evals/d1-suite.json --board scenarios/boards/d1-old.json --out baseline.json
python -m rein results baseline.json --markdown

The number did not move

The check is a patch in rein/examples/h13-process-check/. Apply it, run the suite with it, and then revert it:

git apply rein/examples/h13-process-check/write-before-read.patch
python -m rein eval --eval scenarios/evals/d1-suite.json --board scenarios/boards/d1-old.json --out extension.json
python -m rein results extension.json --markdown
git apply -R rein/examples/h13-process-check/write-before-read.patch

The table is the package's own output. It is scripted, so it repeats exactly. The run with the check printed the same rows.

That is a null result: ten of ten on all five tasks, before and after. The check had nothing to catch. Each held-out task reads all three files before it writes them, and the example tasks use edit_file, which the check does not count. The suite cannot tell a careful run from a careless one, because every script in it is careful.

Without JavaScript, the question is: the table shows the same numbers before and after your change. What goes on the brag sheet?

  1. The process check does not work.
  2. The suite could not show the check's effect, because no trial wrote a file it had not read. The result is a null on this suite.
  3. The check is better, because it is stricter.

Make sure the check can see

A null is only useful if the check works. So the course adds one control task outside the suite: its script writes each file before it reads it, and its checks are the same. Its files are in rein/examples/h13-process-check/scenarios/. Under the baseline it passes ten of ten. With the check it passes none. Tokens and outcomes are the same in both runs, so the process is the only thing the check changed. The check works, and the suite is why the number did not move.

Run the control on your machine, without the check and then with it:

python -m rein eval --eval rein/examples/h13-process-check/scenarios/evals/d1-control.json --board scenarios/boards/d1-old.json --out control-baseline.json
git apply rein/examples/h13-process-check/write-before-read.patch
python -m rein eval --eval rein/examples/h13-process-check/scenarios/evals/d1-control.json --board scenarios/boards/d1-old.json --out control-extension.json
git apply -R rein/examples/h13-process-check/write-before-read.patch

Without JavaScript, the question is: why run a control task when the number did not move?

  1. To show the check works, so the null is about the suite and not about a broken check.
  2. To raise the pass count, since a control is an easier task.
  3. To keep the null off the brag sheet.

An example report

Question: does a write-before-read check change the D1 pass count? Method: the baseline and the check, with trial k on seed k, for k from 1 to 10, scripted, so the numbers repeat. Results: the table above, unchanged. Null: no trial wrote a file it had not read, so the check had nothing to catch. Control: one task that writes first passes ten of ten without the check and none with it. Limit: the suite holds no careless run, so this says nothing about how often a real agent writes before it reads. Next: a suite with a careless tape, scoped the same way.

Now scope your own: the self-check in Keep asks for the criterion and for the line you would write if the number did not move.

Keep it

Extend where the evidence points.

What does the course rank extensions by?
Learning value, and what the extension shows a reviewer you can do. The ranking is the course's judgment and claims nothing about the job market.
What are the parts of a criterion?
The question, the command and seed, the decisive number, and the rule for reading the number.
Why write the prediction before the run?
So a null can be read. You can see what you expected, and compare it with what happened.
What is a null result?
A result that shows a change did not move the number on the suite you ran. It is a finding, and it goes in the report.
What does a control task show?
That the check can see what it measures. A null is then about the suite, not about a broken check.
Why can a scripted run not decide a change to a tool description?
A scripted model replays its replies whatever the description says, so the number cannot move. Only a live run can show that effect.

Your own criterion

Now scope your own. Pick an extension from the list, or another you can measure with the package, and write its parts before you open any code.

  1. Write the criterion for your own extension before you write any code. Say what it changes, the command and seed, the number that decides, and the rule for reading it.
  2. The numbers did not move after your change. Write the line for the brag sheet and the first sentence of the report.
