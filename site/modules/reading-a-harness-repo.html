Reading a real harness repository

An unfamiliar harness is easier to read in a set order. This module reads a small real repository in that order, quoting each part at a fixed tag.

  • Loop & state
  • Tools
  • Observability

60 minutes

By the end you can

  1. Read an unfamiliar harness in a set order: the loop, the model adapter, tools, config, then the trace.
  2. Locate each of the eight wires in a real repository, or note that it is missing.
  3. Run the harness locally on a toy task (with its test model or your own key) and read its trajectory.
  4. Propose one change and say how you would measure it.

Where to start in a repository you have never opened

A regression report says the same model is worse after a harness change. You have never opened this repository. Predict where you start.

Without JavaScript, the question is: A regression report says the same model is worse after a harness change. You open an unfamiliar repository. Where do you start?

  1. Read every file in alphabetical order.
  2. Find the loop, then follow the path the tool output takes to the model.
  3. Start with the test files.

The reading starts where the incident did. Find the loop, then follow the output toward the model. The rest of this module keeps to that order.

The code tour: loop, adapter, tools, config, trace

A code tour is a fixed order for reading an unfamiliar harness: the loop, the model adapter, the tools, the config, and then the trace. The order matters because each part is called from the one before it. This module follows mini-swe-agent at tag v2.4.6, a small harness released under the MIT licence, and every quote below is copied from that tag.

The loop

The loop is a while True that calls one step at a time. Each step asks the model for a reply and runs what the reply asks for.

        while True:
            try:
                self.step()

Source: src/minisweagent/agents/default.py, lines 96 to 98, at v2.4.6

The step itself is short. It queries the model, then executes the actions in the reply.

    def step(self) -> list[dict]:
        """Query the LM, execute actions."""
        return self.execute_actions(self.query())

Source: src/minisweagent/agents/default.py, lines 126 to 128, at v2.4.6

The loop has brakes, and they sit in the model call. Before each query, a step limit or a cost limit that has been reached raises LimitsExceeded.

        if 0 < self.config.step_limit <= self.n_calls or 0 < self.config.cost_limit <= self.cost:
            raise LimitsExceeded(

Source: src/minisweagent/agents/default.py, lines 132 to 133, at v2.4.6

The model adapter

The loop does not call a provider directly. It calls a model object that follows a small protocol: a query method that takes the messages and returns a reply.

    def query(self, messages: list[dict[str, str]], **kwargs) -> dict: ...

Source: src/minisweagent/__init__.py, lines 48 to 48, at v2.4.6

Where the done check is

Finishing is a check on output. The environment reads the first line of the command's output, and if it is the marker and the command returned zero, the run is finished. The config's instructions ask the model to print the marker.

    def _check_finished(self, output: dict):
        """Raises Submitted if the output indicates task completion."""
        lines = output.get("output", "").lstrip().splitlines(keepends=True)
        if lines and lines[0].strip() == "COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT" and output["returncode"] == 0:

Source: src/minisweagent/environments/local.py, lines 45 to 48, at v2.4.6

    6. Submit your changes and finish your work by issuing the following command: `echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT`.

Source: src/minisweagent/config/default.yaml, lines 32 to 32, at v2.4.6

The loop itself does not run the tests. The check that the work is done is the marker, and nothing in the default loop verifies the change. Write that down as a finding: the verification wire is missing from this loop. A real repository may hold a check elsewhere, so you look before you call a wire absent.

Without JavaScript, the question is: In the default loop of this repository, where is the check that the work is done?

  1. In the model's own reply.
  2. In the environment: the output marker is checked, and the loop does not run the tests.
  3. In the config file.

The trace

When a path is given, the save step writes the trajectory. The saved information holds the exit status and the submission, and the rest of the data holds the messages and the cost.

    def save(self, path: Path | None, *extra_dicts) -> dict:
        """Save the trajectory of the agent to a file if path is given. Returns full serialized data.
        You can pass additional dictionaries with extra data to be (recursively) merged into the output data.
        """
        data = self.serialize(*extra_dicts)
        if path:
            path.parent.mkdir(parents=True, exist_ok=True)
            path.write_text(json.dumps(data, indent=2))
        return data

Source: src/minisweagent/agents/default.py, lines 182 to 190, at v2.4.6

                "exit_status": last_extra.get("exit_status", ""),
                "submission": last_extra.get("submission", ""),

Source: src/minisweagent/agents/default.py, lines 174 to 175, at v2.4.6

Running the harness is a step you do on your own machine. It needs a model you can reach, either your own key or a test model.

Runs on your machine, not in the browser.

from pathlib import Path

# agent is the agent object your run created; a path makes the save step write the file.
agent.save(Path("trajectory.json"))

Without JavaScript, the question is: After a local run, where does the trajectory come from?

  1. The agent's save step, when an output path is set.
  2. The model's log on the provider's side.
  3. The test output.

Locate the wires in the repository

Place each place in the repository on the wire it serves. A wire with no place in the repository is a finding, not a blank: write down where you looked.

Check your reading

Answer each question. The reason for each answer shows after you choose.

Without JavaScript, the question is: In an unfamiliar harness, which file do you open first?

  1. The loop.
  2. The tools.
  3. The config.

Without JavaScript, the question is: You want to add a verification gate to the default loop. How do you know it helped?

  1. Add it and read one run that looks good.
  2. Bench it against the old loop on the same seeds, and compare the pass counts.
  3. Remove the cost limit, since the gate makes it unnecessary.

Keep it

Find the loop first.

In what order do you read an unfamiliar harness?
The loop, the model adapter, the tools, the config, then the trace.
What do you do when a wire is missing from a repository?
Write it down as missing, with the file you looked in. A missing wire is a finding too.

  2. You ran the harness on a toy task and the run looks wrong. What do you read, and what change would you propose?
