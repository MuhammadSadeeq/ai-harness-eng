What a harness is

An agent is a model inside a harness. When results change, the cause can be the model or the harness, and you have to find out which.

The same model, a worse result

The task is to make one test pass. The model is the same as before. The only change is in the harness. Predict what happens to the results.

Without JavaScript, the question is: the model stays the same, but the output cap is changed. What happens to the results?

  1. Nothing changes, because the model is the same.
  2. The model got worse, so the results drop.
  3. The results drop, because the harness hides a line the model needs.

The model guessed a port and ended the run as done. The test still failed. The model did not get worse. A cap in the harness cut the one line that explained the failure.

Where the model stops and the harness starts

The model reads a request and writes text. It scores the next token and chooses one, and it can ask for a tool. Everything else is the harness: the loop that calls the model, the tools it can ask for, the permissions that decide what runs, the checks that judge the result, and the limits that cut what the model sees. Building and tuning that is harness engineering. Agent = Model + Harness.

Three words get mixed up. Prompt engineering is choosing the words of the instructions. Words guide the model; they do not enforce anything. Context engineering is choosing what goes on the desk for each call, and what gets cut or saved. Anthropic defines context engineering as curating and maintaining the optimal set of tokens during LLM inference. Harness engineering is wider than both: it includes the desk, the words, and everything that runs around them.

Two kinds of harness show up in practice. The product harness is the one a vendor ships with its model product. The user harness is the one you add around a product or an API: your loop, your tools and your checks. A framework supplies ready-made parts for building either. It does not decide your harness for you.

A useful picture is the operating system. The model is like a program, and the harness is like the system that starts it, gives it access to files, limits its resources and records what it did. The picture gets you far. It breaks at one point: a program runs the same steps each time, but a model writes different text on each run. So the harness has to check what the model produced, and the operating system picture hides that check.

What counts as evidence? The incident is one comparison, and it has the shape a fair test needs. The same model ran the same task twice, and only the harness changed. The old board passed; the new board did not. The course's runs are scripted, so they repeat exactly. Real models vary, and one comparison is not a general result. A fair counterpoint is that a harness change can help one kind of task and do nothing for another, so the effect depends on the task as well.

Check your reading

Answer each question. The reason for each answer shows after you choose.

Without JavaScript, the question is: which of these is context engineering?

  1. Choosing which tool results the model sees on each call.
  2. Writing the instruction at the top of the prompt.
  3. Adding a retry after a timeout.

Without JavaScript, the question is: which of these does the harness do, and not the model?

  1. Chooses the next token.
  2. Enforces a permission before a command runs.
  3. Writes a sentence that sounds sure.

Without JavaScript, the question is: where does the operating-system picture of an agent break down?

  1. An operating system has a scheduler, and a harness does not.
  2. A program runs the same steps each time, but a model writes different text on each run, so the harness must check it.
  3. A process has no memory, and a model has none either.

Without JavaScript, the question is: a vendor ships a model product, and your team adds its own checks around it. Which harness are the checks?

  1. The product harness.
  2. The user harness.
  3. The framework.

Without JavaScript, the question is: what would count as evidence that a harness change alone moves results?

  1. The same model, the same tasks and seeds, two harnesses, and different pass rates.
  2. A new model in the old harness that scores higher.
  3. One run with a worse answer.

Without JavaScript, the question is: which statement is a fair counterpoint to "harness changes move results"?

  1. A harness change can help one kind of task and do nothing for another, so the effect depends on the task.
  2. Harness changes never move results once the model is strong.
  3. Only the model matters; the harness is a wrapper.

Keep it

Agent = Model + Harness.

What is prompt engineering?
Choosing the words of the prompt and the instructions. Words guide the model; they do not enforce anything.
What is context engineering?
Choosing what goes on the desk for each call, and what gets cut or saved.
What is a user harness?
The harness you add around a model product or API: your loop, your tools and your checks.
Where does the operating-system picture break down?
A process runs the same steps each time. A model writes different text each run, so the harness must check its output.
