Long-running agents

A task that outlasts one session needs a record of its state. Learn what the next session can read, and write the note that lets it act without guessing.

  2. Use the initializer pattern: a first session that sets up the environment, a feature list and a progress file.

  4. Write a handoff note the next session can act on without guessing.

The next shift rewrote the parser

Session one fixed the parser and wrote a note for the next shift. The next shift has no memory of session one. Predict what it does first.

Without JavaScript, the question is: session one fixed the parser and wrote a note. Session two starts with no note in its request. What does it do first?

  1. It reads the note, and keeps the parser as it is.
  2. It rewrites the parser, because it does not know the parser is done.
  3. It runs the tests and stops, since they were the last thing done.

The note was written. It never reached the next session, so the next session guessed. The guess broke the parser, changed the migrations and wrote a report that skipped the tests. The run ended done, and the checks said otherwise.

What a new session can read

A long-running agent works on a task that runs over more than one session. A session is one run of the harness, from its first request to its end. Each new session starts with a new context, and it has only what the harness sends. The shift-worker problem is that simple: nothing carries over unless someone writes it down and passes it on.

Without JavaScript, the question is: a new session begins on a long task. What tells it what the last session did?

  1. Its own memory of the last session.
  2. The progress file, which the harness passes into the new session.
  3. The model's summary of the last session, in its own words.

A progress file is that record. It says what is done, what is next and what is open. Anthropic says the claude-progress.txt file, alongside git history, lets a fresh agent quickly understand the state of work.

The first session has a different job. An initializer agent sets up the environment: the files, a feature list of the work, and a progress file. Anthropic's initializer agent runs the first session with a specialized prompt that sets up the environment, including init.sh, a progress log file and an initial git commit. Later sessions start from a known state.

Without JavaScript, the question is: what is the first session of a long task for?

  1. Finishing as much of the task as the window allows.
  2. Setting up the files, a feature list and a progress file, with an initial commit.
  3. Testing every feature before any work starts.

Long work also splits into roles. A planner writes the steps and their order. A generator does each step. An evaluator grades each step against criteria the generator did not write. The split is the point: a generator that grades itself passes its own blind spots.

Without JavaScript, the question is: who grades each step of a long task?

  1. The generator, since it did the work and knows it best.
  2. A separate evaluator, with criteria written outside the generator's work.
  3. Nobody: the done claim at the end of the last session is the grade.

A handoff note is what the next session acts on. It names the next step on one line, the files to start from, and what is already done. Without those three, the next session has to guess, and a guess is how the parser got rewritten.

Without JavaScript, the question is: a handoff note says only "Next: fix the bug." What is missing?

  1. Nothing. The next session will work out which bug.
  2. Which bug, which files to start from, and what is already done.
  3. A longer note with every line of the work.

Write the handoff

The lab is a next shift that reads only the note you write. It needs four things in the note: the parser is done, the migrations stay as they are, the tests run before the report, and the shift knows where it stands. Write a note that holds them, then start the next shift. The lab shows which items the note was missing, and what the next shift did without each one.

The next shift is a script, so every trial repeats exactly. What it does without a note is the course's model, not a measurement of any model.

Prove it on the same shift

The old board runs two sessions with no progress file. The new board passes the progress file into each session. The bench runs the same two sessions on both boards.

These runs are scripted, so they repeat exactly. A real model may read a long note differently, and a real progress file can grow too long to pass whole. Both are reasons to keep the note short and specific.

Keep it

Leave the desk ready for the next shift.

Does a new session remember the last one?
No. It has what the harness sends: the task, the tools, and any progress file the harness passes in.
What is the shift-worker problem?
Each session starts with no memory of the last. The work has to be written down, or the next session redoes it or breaks it.
What does an initializer agent set up?
The environment, a feature list and a progress file, with an initial commit that shows what was added.
What is a progress file for?
It says what is done, what is next and what is open, so a fresh session finds the state without guessing.
Why is the evaluator a separate role?
Its criteria come from outside the generator's work, so it does not pass its own blind spots.
What must a handoff note name?
The next step on one line, the files to start from, and what is already done.

  1. A long task spans three sessions. What does each session need from the one before it, and what does the first session set up?
  2. Who grades the work of a long task, and what does a handoff note have to say so the next session can act?
