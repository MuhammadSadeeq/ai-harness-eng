Observability: traces you can read

A trace records what ran, in order, with what it cost. When a bill is high, the trace says which part of the run to read first.

  • Observability

50 minutes

By the end you can

  1. Record the events that matter, with ids, timing, tokens and cost.
  2. Read a trace and find the first event where things went wrong.
  3. Structure a trace as spans (run, turn, model call, tool call) and map them to the OpenTelemetry GenAI conventions.
  4. Redact secrets before they reach the trace.
  5. Answer “where did the time and money go?” from a trace.

A bill nothing explains

The run passes and the check is green. The bill is far higher than a run that reads one log and writes one line should cost. Predict where the cost sits on the old board, seed 0.

Without JavaScript, the question is: on the old board, seed 0, the run passes. Which event is the first to show the bill was large?

  1. The first model call, because it has the most tokens.
  2. The second turn's cost event, which names messages[2], the log.
  3. The run_end event, which holds the total.

The run did not do anything wrong. It read one log and wrote one line. The bill came from the log being sent again on each call after the read, and the trace is what shows it.

A trace is events, arranged as spans

The harness writes an event as it runs: a model call, a tool call, a permission decision. Each has a sequence number and a time. A span is a timed piece of work built from those events, with a name, a start, an end and a parent: the run, its turns, its model calls and its tool calls. A trace id ties one run's spans and events together.

A log line says what happened. A trace also says which call it belongs to, when it ran and what it cost, so you can read the order of the run. Logs alone are not enough.

Without JavaScript, the question is: which record should the trace hold for each tool call, so you can read it later?

  1. Only the tool's name.
  2. The tool's name, its input, its result, and its time, with a sequence number.
  3. Nothing; the model's reply already says what it did.

OpenTelemetry is an open standard for traces, metrics and logs. Its GenAI semantic conventions name generative AI spans and their attributes. The OpenTelemetry GenAI semantic conventions registry manifest declares stability: development. The names can still change, so check the version before you rely on one.

The course's run, turn, model call and tool call spans are its own structure. Their names follow the conventions. The inference client span name SHOULD be '{gen_ai.operation.name} {gen_ai.request.model}'.

Without JavaScript, the question is: a model call is made to claude-sonnet-5-5. Under the GenAI conventions, how is its inference span named?

  1. chat claude-sonnet-5-5
  2. inference
  3. model_call

The attributes say the counts. gen_ai.usage.input_tokens counts the tokens used in the GenAI input (prompt). gen_ai.usage.output_tokens counts the tokens used in the GenAI response (completion).

Without JavaScript, the question is: which GenAI attribute counts the prompt's tokens?

  1. gen_ai.usage.input_tokens
  2. gen_ai.usage.output_tokens
  3. gen_ai.system

A cost attribution event follows each model reply. It splits that call's cost into its input, output and cache parts, and names the largest part of the request by tokens: the system prompt, the tools, or one message by its index. The bill is the sum of those calls, so the largest part is where to look.

Without JavaScript, the question is: the bill is high. Which field of a cost event says where the money went?

  1. top_part, with top_tokens
  2. The task in run_start.
  3. The window size.

A redaction replaces a secret with a placeholder before the event is stored. It changes the trace. It does not change what the model is sent, and it does not change the bill.

Without JavaScript, the question is: a tool result contains a deploy token, and the trace is written to a shared folder. What must happen before the event is stored?

  1. Redact the token before the event is stored.
  2. Nothing. The model needs the token, so the trace needs it too.
  3. Delete the trace file after the run.

Find the costly part, then write the spans

The replay steps through the old board's run, seed 0. Each reply's cost event sits under its turn. Find the one with the largest call cost, and read the part it names.

Now build the structure yourself. Turn a list of events into the run, its turns, its model calls and its tool calls, each with its parent and its end.

Apply the fix the bill points to

The cost event named messages[2], the log. On the new board the tool output is capped at 400 tokens. The cap keeps the first and last 800 characters and cuts the middle, so the error at the end survives. Redaction stays on, so the secret is replaced in the stored trace.

Keep it

If it isn't in the trace, it didn't happen.

Three wrong ideas to drop: logs are enough; record everything raw; traces are only for incidents. A trace you read after a bill is the same kind of record as one you read after a failure.

What is a span?
A timed piece of work with a name, a start, an end, attributes and a parent.
Where does cost attribution say the money went?
In the cost event after each model reply: top_part names the largest part of the request.

Say it out loud

  1. A run cost much more than you expected. Walk me through how you find the cause from the trace, and in what order.
  2. What does a span record for a model call, and what must never reach the trace? How would you answer where the money went?
