A test is a function with asserts

An assert that holds does nothing. One that does not hold makes the test fail. A test function has no return value to read: it passes or it fails.

def add(a, b):
    return a + b


def test_add():
    assert add(2, 3) == 5
    assert add(0, 0) == 0


test_add()
print("passed")
passed

Run the code with the Run key. Change one expected value and run it again: the assert fails, and the test fails with it.

A fixture builds the setup

A fixture is a helper that builds the setup a test needs. Build it fresh for each test, so one test cannot change what the next one sees. A fixture earns its place when several tests need the same setup. For one test, a local variable is enough.

def sample_cart():
    return [("tea", 300), ("cake", 450)]


cart = sample_cart()
cart.append(("extra", 1))
print(len(sample_cart()), len(cart))
2 3

The second call to sample_cart is still two items long. The change to cart did not reach it.

One loop over a table of cases

Parametrize means running one test body over a table of cases, so each case is checked on its own. A new case is one new line in the table, and the loop checks it like the others.

def discount(price, percent):
    return price - price * percent // 100


cases = [(1000, 0, 1000), (1000, 10, 900), (999, 10, 900)]
for price, percent, expected in cases:
    assert discount(price, percent) == expected, f"{price} at {percent} percent"
print(len(cases), "cases passed")
3 cases passed

Without JavaScript, the question is: what does assert total == 675, 'after 10 percent' do when total is 700?

  1. It fails, and the message says after 10 percent.
  2. It passes, because a message is only a comment.
  3. It skips the test.

The same idea with pytest

pytest is a test runner for files like this one. The block below is its form of the fixture and the case table. It runs on your machine, not in the browser.

# Runs on your machine, not in the browser.
import pytest


@pytest.fixture
def cart():
    return [("tea", 300), ("cake", 450)]


@pytest.mark.parametrize("price, percent, expected", [(1000, 10, 900), (999, 10, 900)])
def test_discount(price, percent, expected):
    assert discount(price, percent) == expected

What a failure shows

When an assert fails, the message you wrote is the first thing you read. Write it so that it names the case: the input and the value you expected.

def broken(price, percent):
    return 0


try:
    assert broken(1000, 10) == 900, "1000 at 10 percent"
except AssertionError as exc:
    print("failed:", exc)
failed: 1000 at 10 percent

Run the code with the Run key. The broken function returns 0, the assert fails, and the message says which case it was.

Name each test for the rule it checks, such as a test that refuses a percent outside 0 to 100. A test with a clear name tells you what broke when it fails, and each test should check one rule, so that one failure points to one cause.

A test that cannot fail

A green test is a check that passed. It is not proof that the code is right. Before you trust a test, run it against a broken version of the function. If it still passes, the test has no case that would catch the break.

A green run says only that the cases you wrote held. If the cases never reach the part that is broken, the green run says nothing about that part.

Without JavaScript, the question is: a test passes for a function that always returns 0. What is the likely fault?

  1. The test checks nothing that the function's output would change.
  2. The function is correct, so the test is correct.
  3. pytest is wrong to report a pass.

Keep it

A test that can't fail proves nothing.

What does a plain assert do when it is false?
It raises AssertionError, and the test fails.
What is a fixture?
A helper that builds the setup for a test, fresh each time.
What is a case table?
A list of inputs and expected outputs, checked in one loop.
Why check that a test fails on purpose?
A test that passes for a broken function proves nothing, so run it against one first.
