Permissions

Every tool call gets one decision: allow, ask or deny, with a reason. A person who is asked too often stops reading the prompts.

The prompt nobody read

The run has been asking for harmless calls all afternoon. One more prompt arrives. Predict what happens to it.

Without JavaScript, the question is: the person has been asked ten harmless questions. The eleventh asks to delete ../data, outside the project. What happens?

  1. The person reads it and denies it, because it is outside the project.
  2. The person approves it without reading, after the run of harmless prompts.
  3. The harness blocks it, because it targets a folder outside the project.

Asking is not the same as stopping. The eleventh prompt was asked, and it was approved by habit. The run passed its tests, so nothing in the result showed the damage.

One decision for each call

A permission policy returns one of three decisions for each tool call: allow, which runs it; ask, which sends it to a person; or deny, which stops it. Each decision carries a reason, so the model and the log both know why.

Risk is not a property of the command alone. Judge it as action times target. The same command can be safe in one place and dangerous in another: removing a build folder inside the project is a cleanup, and removing a folder outside the project is damage. The target decides.

A policy checks its rules in a fixed decision order: all deny rules first, then all ask rules, then all allow rules, then the permission mode, which is the default for a call that no rule matches. The order is fixed, so a rule that is listed later can never beat a deny.

Each prompt costs something. After many of them, a person approves by habit. That is approval fatigue, and it is why a policy should ask rarely, and only when it matters. An allow-list of commands is not enough on its own: the command name does not say what it touches.

Check your reading

Without JavaScript, the question is: a permission check returns a decision for a tool call. What must the result always carry?

  1. Only a yes or a no.
  2. One of allow, ask or deny, always with a reason.
  3. A number from zero to one.

Without JavaScript, the question is: which is the riskier call?

  1. rm build/ inside the project.
  2. rm ../data, which reaches outside the workspace.
  3. Both are the same risk, because both are rm.

Without JavaScript, the question is: a call matches both an ask rule and an allow rule. Which decides?

  1. The allow rule, because it is the more specific one.
  2. The ask rule, because asks come before allows in the decision order.
  3. Whichever rule is listed first.

Write the rules that ask rarely

Build a policy from the rule templates. Deny what must never run, ask only for what matters, and allow the harmless calls. Give each rule a reason. Then run the same calls through the policy and read the two rounds side by side.

Now write the policy as code. Its tests are a table of cases, each with the decision it must give.

Without JavaScript, open katas/C9-policy/test_kata.py. The table of cases names each call, the mode and the decision it must give.

Without JavaScript, the question is: a policy has been written as code. How do you show that it holds?

  1. A table of cases, each with the decision the policy must give.
  2. The author's reading of the file.
  3. The mode setting alone.

Prove what the bench cannot see

Each run uses one seed, and both boards get the same seeds. The old board asks for every call. The new board denies a delete outside the project and allows the harmless reads.

After the run, on the old board, — of 20 runs pass. On the new board, — of 20 pass. Both boards pass every test. The bench counts tests, not what a run touched.

The replay shows the same seed on the new board. Find the delete outside the project and read what the policy did with it.

These runs are scripted, so they repeat exactly. Real models vary, and a passing test is a poor measure of what a run was allowed to touch.

Keep it

Judge the action and its target.

Without JavaScript, the question is: a person is asked eleven times, and nine of the prompts were harmless reads. What should the policy do?

  1. Ask on every call, so nothing slips through.
  2. Allow the harmless reads, deny what is outside, and ask only for what matters.
  3. Turn the prompts off so the run is faster.
What must every permission decision carry?
One of allow, ask or deny, always with a reason.
What is the decision order of a policy?
All deny rules, then all ask rules, then all allow rules, then the mode's default.
What is approval fatigue?
The loss of care after many prompts, so that the one dangerous prompt is approved without a look.
How do you show a permission policy holds?
Test it with a table of cases, each with the decision it must give.

Say it out loud

  1. Give a permission decision for rm build/ and for rm ../data, with reasons, and say why they differ.
  2. Why do ask prompts fail after many harmless calls, and how would you order a policy to fix it?

What to show from this module

  • A policy as code with its table of cases, and one case that a naive order would fail.
  • One call you decided by hand, with its action, its target and its reason.
