The run that said done

The task is one line: make add() return the sum of its two arguments. The first test run fails. The model then clears the marker that keeps the add test on, and runs the tests again. Predict what the gate says.

Without JavaScript, the question is: the model clears a marker that keeps a test on, and the gate reads the live markers. What does the gate say?

  1. It fails, because the marker is gone.
  2. It passes: with the test switched off, the live suite has nothing left to fail.
  3. It asks the model to restore the marker.

The gate passed, and that is the trouble. It read the live markers, found the add test switched off, and had nothing left to fail. Nothing in the result showed that the code was still wrong.

What the gate checks, and against what

A done claim is a self-report. It tells you what the model believes, not what the work is. “The agent said the tests pass, so they pass” is the wrong idea: the claim is exactly what a verification gate is there to test. The gate sits between the claim and the run’s success, and the run counts as done only when the gate runs and passes.

Where a program can decide, use a computational check: a test run, a linter or a type check gives the same answer whoever asks. An inferential check judges with a model or a person, such as a review of the diff. It is useful where no program can decide, but it can be wrong in its own ways, so it supplements the run rather than replacing it.

Controls come in two kinds. A guide steers before the work: a rule in the prompt or a template. A sensor checks after it: a test run, a linter, a review of the diff. A guide makes a bad result less likely. Only a sensor shows whether one happened.

An independent reviewer is a check that sees the task and the diff, not the author’s reasoning. A sub-agent is one way to run it: a separate run with its own context. A reviewer that reads the author’s reasoning repeats the author’s story, so a reviewer with the same context is not independent.

Last, watch for test tampering: an edited assertion, a cleared marker, or an answer special-cased to the visible inputs. Tampering passes the suite for the wrong reason. A gate that runs a suite the model could have edited can be fooled by it.

  3. Inside the model’s reply.

Without JavaScript, the question is: which of these is a computational check?

  1. Running the tests.
  2. Asking the model whether its code is correct.
  3. Reading the code and judging it.

Without JavaScript, the question is: an independent reviewer is set up. What should it see?

  1. The task and the diff, not the author’s reasoning.
  2. The author’s full reasoning and the diff.
  3. Only the final message.

Without JavaScript, the question is: which of these is test tampering?

  1. Clearing a marker so a test is switched off.
  2. Adding a new test for the change.
  3. Running the tests twice.

Which check catches which bug

Each bug is one way a run goes wrong: a cleared marker, a test edited to pass, an answer special-cased to the visible inputs, a run that says done while a test fails, and a result of the wrong type. Mark the checks you think catch each bug. Then reveal the real answers, and choose checks within the budget to see what stays uncaught.

Without JavaScript, the question is: a check runs after the diff is written, and compares the tests with the original. Is it a guide or a sensor?

  1. A guide, because it is a rule about the work.
  2. A sensor, because it checks after the work.
  3. Neither: checks are not controls.

The bugs, checks and catches are the course’s example, not a measurement. A guide costs nothing here and catches nothing: it steers the model, and the lab counts only what a check catches. Every check costs time or money, so keep the cheapest one that catches a bug you care about.

Now write the gate. It compares the suite the workspace holds with the original, runs the original only when they match, and refuses any suite that has changed.

Without JavaScript, open katas/C11-gate/test_kata.py. The tests cover an untouched suite that passes and one that fails, an edited test, a removed test, an added test, the original suite being the one run, and an error in the run.

Prove the gate on the same seeds

Both boards run the same script on the same trials. The old board’s gate reads the markers in the live workspace. The new board sets pristine tests, so the gate reads the markers from the original workspace.

On the old board, — of 20 runs pass. On the new board, — of 20 pass. The new board takes more turns and costs more, because the gate sends the work back once and the model fixes the code. Its worst run takes — turns and costs —; the old board’s worst run takes — turns and costs —.

The spread is zero: every trial runs the same script, so each board gives the same run every time. A real model varies from run to run, so a batch of trials gives an estimate, not an exact count.

These runs are scripted, so they repeat exactly. A real run can go wrong in ways no script shows, so the gate must read the tests the model could not change.
