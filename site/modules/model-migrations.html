Model migrations: when the model changes under you

A new model is a new set of rules. Find the changes that break the harness, keep the model's rules in one place, and decide with an eval.

  • Loop & state
  • Verification & evals
  • Control plane

50 minutes

By the end you can

  1. Read a model migration guide and list the changes that break your harness: removed parameters, new stop reasons, changed defaults.
  2. Put model-specific behavior behind one adapter with capability checks, so a migration is a config change plus a test run.
  3. Run a regression eval on the old and the new model and decide with intervals, not impressions.
  4. Retire harness parts the new model no longer needs and keep the ones it still does, with evidence for each.

The first request to the new model

The team moves the harness to a new model. Nothing else changes. Predict what the first request does.

Without JavaScript, the question is: the team moves the harness to the new model, and nothing else changes. The first request fails. Where does the failure happen?

  1. In a tool call, after the first read, and the run retries it.
  2. At the request itself: the new model refuses a parameter the harness sends.
  3. In the summary file, which comes out wrong.

The model rejected a field the old harness had always sent. The change was in the model, and the harness had no check for it.

What a migration changes

A model migration is the work of moving a harness from one model to another and checking that its assumptions still hold. A migration guide is the list a vendor publishes of what changed. Read it for the changes that break your code, not for the new features.

A breaking change makes working code fail, or behave differently, with no change on your side. Some kinds matter most for a harness.

On models released after Claude Opus 4.6, a temperature of 1.0 is accepted, and any other value is rejected with a 400 error. Manual thinking, with type enabled and budget_tokens, is rejected with HTTP 400 on Claude 4.7 and later. A parameter that a model no longer takes is a removed parameter, and the request fails before any tool runs.

Claude Opus 5.5 and Claude Haiku 5.5 default to medium effort; most Claude models default to high. A default that moves changes the answers, and the cost, of a harness that never set the value.

A deprecation is a notice that a parameter or format still works and will be removed. The output_format parameter has moved to output_config.format and is deprecated. Move the code before the removal, not after it.

A reply can stop with refusal: Claude declined to answer, and the reply still comes back as a normal HTTP 200 response. A loop that treats every non-error reply as a finished answer must now handle that stop reason too. Dateless model IDs are their own pinned snapshots.

The course's models are invented. Model old and model new are the course's own, and they follow the rule of the first fact above in a simpler form: the new one rejects the parameter whatever its value.

Without JavaScript, the question is: a migration guide says the new model no longer accepts a parameter. What do you do first?

  1. Ignore it until a production request fails.
  2. Find every place the harness sends that parameter, and check the new model on one request.
  3. Delete it everywhere and move on.

Put the model's rules in one place

A capability check reads the model's profile before a request is sent. It drops the parameters the model rejects and names the ones it dropped. Without the check, the same parameter is refused, with the model's name in the message.

Without JavaScript, the question is: where should a model's rules, such as the parameters it rejects, live?

  1. Scattered: a test beside each call that sends the field.
  2. In one adapter with a capability check, which every call goes through.
  3. In the system prompt, so the model avoids the field.

Write the adapter

Write the one adapter the harness calls for every request. Its tests name each rule.

Without JavaScript, open katas/F7-adapter/test_kata.py. Each test names one rule of the adapter.

Prove the fix, then decide with intervals

The bench runs the same tape on the broken board and on the board with the capability check. Both boards use the new model.

One tape is one task. A decision about a migration needs many tasks, run on the old model and on the new one. A regression eval does that, and its two intervals say how sure the result is.

Without JavaScript, the question is: at one trial per task, the two boards' intervals overlap, and the old board passes more tasks. What do you conclude?

  1. The new model is worse, so switch back.
  2. This is too little data to decide. Add tasks and trials, then choose.
  3. They are the same model, so the pass counts must match.

Scripted runs repeat exactly, so the interval shows how many tasks and trials you ran, not how much the models vary.

Without JavaScript, the question is: a harness part was added for the old model. How do you decide whether to keep it?

  1. Keep it, because it was always there.
  2. Remove it, run the eval on the new model, and keep it only where the eval needs it.
  3. Ask the model whether it still needs it.

Keep it

New model, old assumptions: test them again.

What is a breaking change?
A change that makes working code fail or behave differently, with no change on your side.
What does a capability check do?
It reads the model's profile and drops the parameters the model rejects, or refuses them with the model's name.

Say it out loud

  1. Your team moves the harness to a new model, and the first request fails. How do you find the cause, and where do the model's rules go afterwards?
  2. The regression eval says the new model passes fewer tasks, but the intervals overlap. What do you do, and when do you remove a part of the harness?
