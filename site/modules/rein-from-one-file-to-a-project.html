From one file to a project

Rein becomes a project you can install, rerun and check. The checkpoints are tests, the package runs trials and evals, a live run is capped, and every change is measured against a baseline.

  • Verification & evals
  • Observability

90 minutes

  1. Turn the build's checkpoints into an automated test suite.
  2. Package Rein as a small project with typed code, tests and an eval runner.
  3. Run a real eval with a real model on a small capped budget and record the numbers with intervals.
  4. Run your first experiment: one harness change, measured against a baseline.
  5. Write a showcase README a reviewer can verify.

A cheaper harness that fails

You change one setting: a turn limit of four. The cost falls on every task. Predict what the held-out tasks do before you read the numbers.

Without JavaScript, the question is: You set the turn limit to four and the cost falls on every task. What do you expect on the held-out tasks?

  1. The same pass rate, only cheaper.
  2. A lower pass rate: the change cut runs that need more turns.
  3. Nothing changes: the tasks are the same.

Keep the prediction in mind. The Do beat has the scripted numbers, and they answer it.

Checkpoints, a package, and a capped live run

Every step's checkpoint is already an expected transcript. Turn it into a test: the step runs in a temp folder, and its output must match. The course runs its checkpoints this way, under CPython and under Pyodide, and each trace is checked against the course's schema.

Without JavaScript, the question is: A checkpoint becomes a test. What does the test check?

  1. That the step's transcript matches the expected output, in a temp folder.
  2. That the code has no bugs.
  3. That the steps pass in the browser only.

Rein is also a package, rein. Run every command on this page from the repository root, which holds scenarios/, site/ and rein/. rein/README.md gives the one-time install and the PYTHONPATH form. Three scripted commands, which run offline and repeat exactly:

python -m rein run --tape scenarios/d1-example-a.json --board scenarios/boards/d1-new.json --seed 0
python -m rein eval --eval scenarios/evals/d1-suite.json --board scenarios/boards/d1-new.json --out d1-new.json
python -m rein results d1-new.json --markdown

The scripted commands repeat exactly and run offline. A live run uses a real model with your own key, and it is shown here, not run: this page spends no money. Your key comes from the environment only, never from the command line and never into git.

export ANTHROPIC_API_KEY=...   # on your machine only
python -m rein eval --eval scenarios/evals/d1-suite.json --board scenarios/boards/d1-new.json --live claude-haiku-5-5 --max-cost-usd 0.05 --trials 2 --out my-results.json

Without JavaScript, the question is: What does --max-cost-usd protect on a live run?

  1. The spend: a request that could pass the cap is not sent.
  2. The model's answers, so they stay short.
  3. The key, so it is never printed.

The cap is checked before each request. A request that could pass the cap is not sent, and the run stops with status budget. The cheap tier's price is what gives the cap its meaning: for prompts up to 100,000 tokens, Claude Haiku 5.5 costs $0.10 per million input tokens and $0.50 per million output tokens. A small cap buys a small sample, and the table should say so.

A demo video is not a portfolio. It shows one run. A reviewer needs commands they can rerun, the seeds, and the cap.

Run the checkpoints, then the experiment

The checkpoint at the end of step 11 is one test in the suite. Run it, then read Break it on purpose: each break's expected output is checked as well, so a break that stops failing is a bug in the suite.

Your first experiment, against a baseline

The experiment is one harness change: a turn limit of four, on board d1-new. The baseline is the same suite on board d1-old, without it. Both run the same five tasks, with the same seeds and ten trials each, through the eval runner. The tables below come from python -m rein results --markdown, and they are scripted: they repeat exactly.

Run the baseline, then print its table:

python -m rein eval --eval scenarios/evals/d1-suite.json --board scenarios/boards/d1-old.json --out baseline.json
python -m rein results baseline.json --markdown

Run the change the same way:

python -m rein eval --eval scenarios/evals/d1-suite.json --board scenarios/boards/d1-new.json --out change.json
python -m rein results change.json --markdown

Scripted: the change, board d1-new

| Task | Passed of trials | Wilson 95% interval | Tokens | Cost | Scripted |
|---|---|---|---|---|---|
| example-a | 10 of 10 | 72.2% to 100.0% | 9,950 in, 560 out | $0.0255 | yes |
| example-b | 10 of 10 | 72.2% to 100.0% | 10,100 in, 690 out | $0.0271 | yes |

| held-out-c | 0 of 10 | 0.0% to 27.8% | 23,200 in, 1,440 out | $0.0608 | yes |

These numbers are scripted: they repeat exactly. A real model's numbers would vary.

Without JavaScript, the question is: A change is measured against what?

  1. A baseline: the same tasks and seeds, without the change.
  2. The author's memory of the last run.
  3. The best of all the trials.

The examples script two replies each, so four turns finish them. The held-out tasks script eight, so four turns cannot finish them. That is why the change cut the cost and also dropped the held-out tasks, from 10 of 10 passing to 0 of 10, on the scripted boards. That is the result to report: a saving and a regression, each with its interval. A bad result is still a result. One good run would have hidden it.

A showcase README a reviewer can verify

A reviewer should be able to check each line of the README. Keep the same structure:

# Rein: one change, measured

What changed: one setting, turn_limit of 4 (board d1-new), against the baseline (board d1-old).
Suite: the D1 suite, five tasks, ten trials each, the seeds in the suite file.
Reproduce: the three commands above, from the repository.
Results, scripted (they repeat exactly): the table from rein results --markdown.
Results, live (your key, your cap): the table from your own run, with the model id and --max-cost-usd.
Not claimed: any real model's numbers beyond your own table; any task outside the suite.

Keep it

Ship the numbers with the code.

What does a checkpoint become in H12?
An automated test: its step runs in a temp folder, and its transcript must match the expected output.
What does --max-cost-usd do on a live run?
It caps the spend. Before each request the run checks that the request cannot pass the cap, and stops with status budget if it could.

  1. Walk me through your first experiment: the change, the baseline, the tasks, and what you would report.
  2. A teammate says one good real run proves the harness works. What do you answer?
