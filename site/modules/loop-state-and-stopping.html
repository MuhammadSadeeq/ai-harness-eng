Loop state and stopping well

A run keeps its state between calls. When it stops, it has to close the books: answer what it started, and record how it ended.

A request the API refuses

The run reads a file and starts to rename a function. A person interrupts it during that tool call. The run resumes. Predict what the next request does.

Without JavaScript, the question is: the run was interrupted during a tool call, and the call got no answer. What does the next request do?

  1. It carries the call, and the missing result is ignored.
  2. The API refuses the request: a tool call has no result right after it.
  3. The harness retries the same call, and it succeeds.

The harness kept going after the interrupt and left the call with no answer. The next request was built with that gap in it, and the API refused it. The run ended as an error, not as a stop the person asked for.

One state, one exit

The run state is everything the run remembers between calls: its messages, its turn count and its status. Keep it in one object, and change it in one place. Then the run has one record of what happened.

Without JavaScript, the question is: which design keeps a run's state easy to trust?

  1. Each function keeps its own copy of the messages and the status.
  2. One state object, changed only through a few functions that take it.
  3. The model keeps the status, and the harness reads it from the reply.

Each way out of the loop is an exit, and each exit sets the final status once. A second exit is refused, so a run never claims two endings.

Final statusWhat ended the run
doneThe model claimed done, and the harness checked the work.
max_turnsThe turn limit was reached.
budgetThe token budget was spent.
loopThe same action repeated, and loop detection stopped it.
interruptedA person asked the run to stop.
errorA request failed, and the run cannot go on.

Without JavaScript, the question is: the turn limit is reached. Which final status should the run record?

  1. error
  2. max_turns
  3. done

An interrupt can leave an orphaned tool call: a call with no result after it. Leaving out the tool_result for a tool_use makes the request fail with the standard error 'tool_use ids were found without tool_result blocks immediately after'. A tool_use block that is not run still needs a tool_result with is_error true and a brief explanation.

To pause and resume a run, save its state, and start again from the saved turn. The saved history only grows at the end, so a resumed run keeps every earlier message as it was.

Loop detection compares the last few calls. When they are the same, the run is going in circles, and it stops before the turn limit does.

Without JavaScript, the question is: a run is paused and must resume later. What must the saved state hold?

  1. Only the final status.
  2. The messages, the turn count and the pending calls, saved together.
  3. Nothing. The model remembers the run.

Without JavaScript, the question is: the last five calls are identical, and the turn limit is far away. What should the loop do?

  1. Keep going, because the turn limit will stop it.
  2. Stop the run, because the same action has repeated, and record why.
  3. Clear the history so the model starts fresh.

Keep it

Close the books before you stop.

What is run state?
Everything the run remembers between calls. It lives in one object, and one function changes it.
What is an orphaned tool call?
A tool call with no result after it. The request holding it is refused.
