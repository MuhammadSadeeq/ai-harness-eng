Rein 6: a context budget

Rein counts the size of each request before it sends it. A tool result that is too big is cut to its start and its end, and old history is compacted once the estimate is over the budget. Each cut is written to the trace.

A flood with nothing to stop it

A tool returns a log of about 11,000 tokens, and the window is 8,000. Nothing in the harness trims the log. Predict what the next call does.

Without JavaScript, the question is: The window is 8,000 tokens. A tool returns a log of about 11,000 tokens, and nothing trims it. What happens on the next call?

  1. Rein cuts the log to fit the window, and the run carries on.
  2. The next prompt is too big to send, and the run fails with an error. The error is the symptom.
  3. The model reads the log and works inside the window anyway.

The log comes back whole. Nothing cuts it, so the next prompt is too big to send. The error is the symptom: the prompt had already grown past the window when it was built.

Count it, cap it, compact it

Rein does three things before it sends a request. It estimates the size of the messages, caps each tool result as it returns, and compacts old history when the estimate is still over the budget.

The first is the token estimate. estimate_tokens() measures the messages as JSON and divides the characters by four. It is a rough count, and it costs no call, so the harness can check the size before every request.

Without JavaScript, the question is: How does estimate_tokens() count the tokens in a request?

  1. It asks the provider for the exact count before each call.
  2. It measures the characters of the messages as JSON and divides by four.
  3. It counts the words in the last message only.

The second is the cap on each result. truncate() keeps the head and the tail of a result that is over tool_output_chars, and puts a line between them that says how many characters it cut. The model still sees how the log begins and how it ends, and the line tells it that the middle is missing.

Without JavaScript, the question is: A tool result is 40,000 characters and the window is small. Which step caps it before it enters the context?

  1. compact(), which replaces the old history with a summary.
  2. truncate(), which keeps the head and the tail and says how much it cut.
  3. estimate_tokens(), which shortens the result when it is big.

The third is compaction. When the estimate is over context_limit, compact() swaps the older history for a short summary of the task and the tools used so far, and keeps the newest messages word for word. The cut never lands between a tool request and its result.

Without JavaScript, the question is: compact() finds that its cut would land right after a tool request. What does it do?

  1. It cuts there anyway, because the newest messages are kept.
  2. It moves the cut back, to one of the model's messages, so a request keeps its result.
  3. It returns the messages unchanged and stops the run.

Why the budget is small, and the four levers in the order to apply them, are in C2 · Context budget. Rein applies the output cap and compaction. It does not decide what the model needs.

Do not wait for a request to fail to learn that it was too big. A refused request was already built and sent; the estimate is how the harness learns the size before it sends.

Each cut, and each compaction that replaces old history, is written to the trace as one event. The event is kind compaction and names the tokens before and after, the number of messages dropped, and the notes kept, so the run can be read after it ends.

Add the budget to rein.py

Step 6 adds a context section to rein.py: the estimate, compaction, the cap in the tool runner, and the check before each model call. The checkpoint runs the find-the-error script with --context-limit 1200, a limit small enough that the run compacts once. It prints the two cuts, the compaction from about 1,310 tokens down to about 751, and the five model calls.

Pass the flood tape with the budget

The flood tape is the one from the break. Bench the old board, which has no output cap, against the new board, which caps the output at 600 tokens, on the same seeds. Read which trials pass on each board.

These runs are scripted, so they repeat exactly. A pass here shows the budget holds on this tape. It does not show that it holds on every log.

Keep it

The smallest window that works.

How does estimate_tokens() count a request?
It measures the characters of the messages as JSON and divides by four. A rough guess, good enough to decide when to act.
What does truncate() keep, and what does it say?
The head and the tail of a result, and a line that says how many characters it cut.

Say it out loud

  1. The window is 8,000 tokens and a tool result is 40,000 characters. What does your harness do before the next call?
  2. Why must the summary step never cut between a tool request and its result?
