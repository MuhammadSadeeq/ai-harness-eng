A reply that asks for a tool, and no tool runs

The model answers with a sentence and then asks for a tool. The sentence is text, and the request comes after it. Predict what the harness does next.

Without JavaScript, the question is: the reply says "I'll run the tests first." and then asks for run_command. What does the harness do next?

  1. It runs the tests, reads the output and keeps going.
  2. It asks the model again, because text before a tool request is not valid.
  3. It ends the run as done. The tests never ran.

The run was marked done on its first turn. The tests never ran, and the checks still fail.

One interface, two models

Rein needs a reply, and it does not care where the reply comes from. So the code calls one model interface: one function that takes the system prompt, the tools and the messages, and returns a reply. A scripted model answers from a fixed list, so every run repeats exactly. A real model makes the same call. The rest of Rein never asks which one it has.

@dataclass
class Reply:
    text: str          # what the model wrote
    tool_calls: list   # the tools it asked for (maybe none)
    # why it stopped: "end_turn", "tool_use", "max_tokens", ...
    stop_reason: str
    content: list      # the raw blocks, exactly as they came
    usage: dict        # input and output token counts


class FakeModel:
    # Replays a script, so every run repeats exactly.
    def call(self, system, messages, tools) -> Reply: ...


class ClaudeModel:
    # The real API, with the same signature.
    def call(self, system, messages, tools) -> Reply: ...

A dataclass holds each reply. The text, the stop reason and the token counts are named fields, so the code reads each one by name. A response's content is an array of content blocks, each with a type that determines its shape. Rein keeps those raw blocks too, because a tool request can come after the text, and the harness has to read the blocks, not only the first one.

The stop reason says why the model stopped. When the model asks for a tool, Claude is calling a tool and expects the application to run it.

Each request starts from what you send

The Messages API is stateless: you send the full conversational history with each request. So a run knows only what its own request contains. Two runs of the same script do not remember each other, and nothing in the API joins them.

The second run is a new request. If you want it to know the first run, the first run's messages have to go in the request again.

Write the interface

Each step adds a few lines to rein.py. A chunk shows the lines it adds. The checkpoint runs your file with the step's command and compares its output with the expected output.

The default model is claude-sonnet-5-5, and you can change it with the REIN_MODEL environment variable. The four current models have the API IDs claude-fable-5-1, claude-opus-5-5, claude-sonnet-5-5 and claude-haiku-5-5.

Prove it on the same seeds

The old board has the first-block bug. The new board has no bug, so it reads every tool request in the reply. Both boards run the same seeds, so the harness is the only difference.

These runs are scripted, so they repeat exactly. Real models vary, and a later module measures that.

Keep it

One interface, many models.

What is a model interface?
One function the rest of Rein calls for a reply. A scripted model and a real model sit behind it.
What is a dataclass?
A Python class with named fields. Rein uses one to hold a reply, so each field has a name.
What does stop_reason tell the harness?
Why the model stopped, such as tool_use or end_turn. The harness decides its next step from it.
Why does Reply keep the raw content blocks?
A reply's content is a list of blocks. A tool request can come after text, so the harness reads the blocks, not only the first.
What does Rein print with each reply?
The stop reason and the input and output token counts, so you can see what each call used.
Is the API stateless?
Yes. You send the full history with each request, and the API keeps nothing between requests.
Three runs of one script. What does run three know about run one?
Only what its own request includes. Nothing carries over by itself.
