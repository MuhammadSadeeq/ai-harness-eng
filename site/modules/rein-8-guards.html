Rein 8: guards that stop the run well

A run needs more than one way to end. Rein gives each guard its own status, so the ending says why, and it closes the books when a run is interrupted, so the history it leaves behind is still valid.

  • Loop & state

40 minutes

By the end you can

  1. Add guards for turns, tokens, time and repeated actions, each with its own final status.
  2. Close the books on interrupt: every pending tool call gets a result.
  3. Show each guard firing on its own tape.

An edit left hanging

The model asks to rename a function, and the user presses Ctrl+C while the edit is pending. The run stops. Predict what the next request must contain.

Without JavaScript, the question is: The user presses Ctrl+C while the model's edit is pending. What must the next request contain?

  1. Only the messages so far, so the edit can be retried next time.
  2. A result for the pending edit, saying it was interrupted, so the history stays valid.
  3. Nothing: an interrupted run sends no next request.

The run stopped, and that was fine. The trouble was the history it left: the edit had a tool request and no result, so the next request carried the gap.

Each guard stops the run with its own status

Every guard writes a guard line with its limit and value, and then the run_end line with its own status. The turn limit ends the run with max_turns. The token budget ends it with budget, before the call that would go over. A Ctrl+C ends it with interrupted. A done reply ends it with done, and a breaker that stays open ends it with circuit_open.

Without JavaScript, the question is: The turn limit and the token budget both stop a run. What does each write before the run ends?

  1. A guard line with its limit and value, then run_end with the guard's status.
  2. Only run_end: the guard is not traced.
  3. A model_error line, because the model ran out of room.

A loop guard works in two steps. The loop detector counts a call that is identical to the one before it. On the third identical call it answers with an error and does not run the call, so the model is told to try something else. If the model repeats that call again after the redirect, the loop guard ends the run with loop.

The C5 simulator stops at the first repeat, and Rein gives the model one warning first, so the limit-2 run ends at turn 3.

A fourth guard counts time on the same clock as the retries. With --max-seconds, Rein checks the clock before each model call, and a run that has taken too long ends with max_time. Under --fake the clock moves only by the waits, so the time guard can fire on the outage tape before the breaker opens.

Without JavaScript, the question is: The model makes the same tool call with the same arguments for the third time in a row. What does Rein do?

  1. It answers with an error and does not run the call.
  2. It runs the call and ends the run with loop.
  3. It removes the call from the history.

An interrupt must leave a valid history. Leaving out the tool_result for a tool_use makes the request fail with the standard error “tool_use ids were found without tool_result blocks immediately after”. A tool_use block that is not run still needs a tool_result with is_error true and a brief explanation. So when the run is interrupted, close_open_calls() gives every pending tool request that result: an error that says it was interrupted before it ran.

Without JavaScript, the question is: The user presses Ctrl+C during a tool run. What does the history look like after the run stops?

  1. Every tool request has a result, so the history is valid.
  2. The pending tool request has no result, and the next call is rejected.
  3. Rein deletes the messages after the last answer.

The theory of stopping well, final statuses and orphaned tool calls is in C5 · Loop state and stopping well.

Add the guards to rein.py

Step 8 adds the loop detector, closes the open calls on Ctrl+C, gives each ending its own status, and adds the token budget. The checkpoint runs the stuck script: the loop detector answers the third identical read, the cut-off reply is continued, and the run ends done after seven calls.

Run the interrupt tape on both boards

The interrupt tape stops the run after the model asks for the edit. The old board closes nothing, so the next request carries the gap. The new board answers the pending call, so the history stays valid. Both boards get the same seeds.

These runs are scripted, so they repeat exactly. A pass shows the repair holds on this interrupt. It does not show that it holds on every interrupt.

Keep it

Every run needs more than one exit.

What does the turn guard end the run with, and what does it record?
The max_turns status. It writes a guard line with the limit and the turn count first.
What does close_open_calls() add after an interrupt?
A tool result for every pending tool request, saying it was interrupted before it ran.

Say it out loud

  1. Name every way a run in your Rein can end, and the status each one writes.
  2. A colleague says a turn limit is all a harness needs. What do you show them?

What to show from this module

  • Your trace.jsonl from the Ctrl+C break, with its interrupt line and run_end line described, and the pending tool call named.
  • The interrupt bench: one trial the old board fails, the history it left, and the repair that changed it on the new board.
