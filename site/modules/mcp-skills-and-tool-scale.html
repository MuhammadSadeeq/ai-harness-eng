Sixteen tools and a wrong pick

The support agent has to look up one ticket and write its status down. Its request carries every tool it might need: write_file and fifteen more. Among them are ticket_lookup, the one the task needs, and ticket_list, a look-alike that lists a customer's tickets. Predict where seed 0 goes.

Without JavaScript, the question is: on the old board, seed 0, the request sends sixteen tool definitions and the task needs ticket_lookup. What does the run do?

  1. It picks ticket_lookup, gets the ticket and writes the answer.
  2. It picks ticket_list, gets an error, and ends without the answer.
  3. It searches for the tool first, then loads it.

The run did not fail on the lookup. It failed when the reply picked ticket_list. Every call paid for all sixteen definitions, and nothing in the request said which one this step needed.

What MCP and skills put in the context

The Model Context Protocol (MCP) connects a model to tools, resources and prompts that other programs offer. The 2026-07-28 index lists Resources, Prompts and Tools as features servers offer to clients. A MCP server offers them. A MCP resource is data a server offers for the model to read.

The client reaches the server over a transport. The transports page describes stdio as newline-delimited messages over the standard streams of a client-launched subprocess. The transports page says each Streamable HTTP message is an HTTP POST to a single MCP endpoint.

The MCP host is the application the user runs, and it decides which servers to connect. The MCP client keeps one connection to one server. The course uses these two roles as its own model. The facts registry defines neither, so treat them as the course's words, not the spec's.

Without JavaScript, the question is: in MCP, which part offers tools, resources and prompts?

  1. The host.
  2. The server.
  3. The model.

A skill is a folder with a SKILL.md file. The Agent Skills specification requires SKILL.md to contain YAML frontmatter followed by Markdown content. The description field is required, with a maximum of 1024 characters, and describes what the skill does and when to use it.

Skills load in layers. That is progressive disclosure. The Agent Skills spec describes progressive disclosure: agents load skills progressively, adding detail only as a task requires it. Under progressive disclosure, the name and description of every skill are loaded at startup (about 100 tokens). A skill is not fine-tuning. Nothing in the model changes; only the text it reads does.

Without JavaScript, the question is: with progressive disclosure, what is loaded at startup for each skill?

  1. The whole procedure.
  2. The name and the description.
  3. Nothing, until the model asks for the skill by name.

Tool definitions work the same way in the request, and they cost more because they come every call. In the simulator, the old board's first request is 1008 tokens with sixteen definitions. The board with tool search sends one definition, and the same request is 163 tokens. Deferred loading keeps a definition out of the request until a step needs it. Both are the course's model, with no product claim.

Without JavaScript, the question is: you add ten tools to a run and the pass rate drops. What do you measure first?

  1. The number of tools, and nothing else.
  2. The tokens each call carries, and the pass rate with and without the tools.
  3. The speed of the model.

A programmatic tool calling idea is that the model writes a short program that calls several tools, so only the program's result returns to the context. That cuts round trips. The course makes no product claim about it.

Without JavaScript, the question is: what does programmatic tool calling change?

  1. The model writes a short program that calls several tools and returns one result.
  2. The model writes its own tool definitions.
  3. The tools run without a permission check.

Before you connect a server, vet it: who wrote it, what it can reach, and how it is pinned. The 2026-07-28 tools page requires clients to treat tool annotations as untrusted unless they come from trusted servers. Pinning a server and checking its source come in E2.

Without JavaScript, the question is: a new server marks its tools as read-only. What do you do before you connect it?

  1. Connect it, because the server says the tools are read-only.
  2. Check who wrote it, what it can reach, and how it is pinned, and treat its annotations as hints.
  3. Connect it, then check the annotations when the run fails.

Load the tool when the step needs it

The fix is in the list, not the model. A search takes the query's words and loads the tools whose name and description contain every word, five at most. A tool already loaded is reported, not loaded twice.

Without JavaScript, open katas/C8-search/test_kata.py. Each test names one search case and what it must return.

Measure it on the same seeds

The old board sends every definition on every call. The new board starts with the search tool alone and loads the lookup tool when the task needs it. Both run the same task on the same seeds.

These runs are scripted, so they repeat exactly. Real models vary, and later modules measure that.

Keep it

Load the menu, not the kitchen.

Three wrong ideas to drop: MCP is a model feature; connecting more servers is free; skills are fine-tuning.

What does a server offer to a client?
Tools, resources and prompts. The client reaches them through a transport.
What does progressive disclosure load up front?
The name and the description of each skill. The full procedure loads when the task needs it.

Say it out loud

  1. A colleague wants to connect a new server and add a skill for deploy checks. Walk me through what each one puts into the context, and when.
  2. Your run sends forty tool definitions with every call, and a lookup step takes five round trips. What do you change, and what do you check before you connect a new server?
